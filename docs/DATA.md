# Data plan

All data is public. Docs: https://formulae.brew.sh/docs/api/ and https://docs.brew.sh/Analytics. The pipeline lives in `scripts/data/`; its output contract is `scripts/data/types.ts`.

## Sources

| Need | Endpoint |
|---|---|
| All core formulae (metadata) | `https://formulae.brew.sh/api/formula.json` |
| All official casks (metadata) | `https://formulae.brew.sh/api/cask.json` |
| Formula installs, ranked (all taps) | `https://formulae.brew.sh/api/analytics/install/{30d,90d,365d}.json` |
| Installs on request (not as a dependency) | `https://formulae.brew.sh/api/analytics/install-on-request/{30d,90d,365d}.json` |
| Cask installs (all taps) | `https://formulae.brew.sh/api/analytics/cask-install/{30d,90d,365d}.json` |
| Dates (added, updated) | git history of `Homebrew/homebrew-core`, `Homebrew/homebrew-cask` and each community tap |
| Community package metadata | the tap's GitHub repo (`owner/homebrew-tap`), read as text |
| Tap description, stars | GitHub REST API `repos/{owner}/{repo}` |
| Package GitHub repositories (link, stars, kind) | GitHub GraphQL `repository(owner, name)`, for the `github.com` repositories in homepages and download URLs (`scripts/data/repos.ts`; rules in `docs/DECISIONS.md`) |
| Mac app icons | [CaskFlow](https://github.com/alielsokary/CaskFlow)'s `icons` branch: `icons.json` lists the cask tokens with a 256px PNG |
| Mac app categories | CaskFlow's latest release: `categories.json` files each official cask under one primary category |

Notes:
- Analytics count **install events** from users who haven't opted out, on macOS and Linux. Show them as relative popularity, always labelled with the period ("Installs · 30 days"), and never as "Mac installs". `meta.json` has each window's exact dates.
- Counts arrive as strings with thousands separators (`"509,747"`).
- Public GitHub **taps are included** in the analytics as `owner/tap/name`. The cask feed that covers them is the undocumented `cask-install/{period}.json`; the documented `cask-install/homebrew-cask/{period}.json` only covers the official tap and has a different shape.
- Around 13,000 community taps show up; about 100 have more than 1,000 installs in 30 days. Brewhunt lists packages from the top 100 taps by installs.
- About 120 analytics names match no current formula: removed packages, plus a few renames, which `oldnames`/`old_tokens` resolve. The rest are dropped (the run logs the biggest).
- Prefer **install-on-request** for the popularity of formulae (avoids libraries pulled in as dependencies). Casks are always installed on request.
- Metadata for community packages is **not** in `formula.json`/`cask.json`. We don't run `brew info` on taps: that would execute third-party Ruby in CI. The pipeline clones each tap and reads `desc`, `homepage`, `version`, `license`, `name` from the `.rb` files as text (`scripts/data/ruby.ts`). Nothing from a tap is executed, symlinks are ignored, and the output is treated as untrusted text.

## Pipeline

`.github/workflows/data.yml` runs daily at 06:17 UTC (and on demand):

1. **refresh** (read-only token, no secrets): `node scripts/data/run.ts` downloads the API files, clones homebrew-core, homebrew-cask and the top 100 taps, looks up package repositories on GitHub, and writes `data/`. It refuses to publish if Homebrew returns something implausible (too few packages, stale analytics).
2. **publish** (can push, runs no pipeline code): commits `data/` to the `data` branch if anything changed.
3. **site**: runs `ci.yml` (lint, tests, `validate:content`, build, deploy) against that data commit.

Every other build (pushes, PRs) checks out the latest `data` branch into `data/`. Locally: `npm run data:pull` (fetch it) or `npm run data` (run the pipeline; add `-- --cache-api` to reuse downloads, set `GITHUB_TOKEN` for tap descriptions).

### Dates
- **Added (`firstSeen`)**: the date the package's file was added on the tap's default branch (merge date, not when the PR was opened). Renames (`oldnames`/`old_tokens`) and file moves don't count as new.
- **Updated (`updatedAt`)**: when the current version landed: the earliest commit whose subject names the version (`wget 1.25.0`, `bump-wget-1.25.0`, `wget: update 1.25.0_2 bottle.`), dated by when it reached the default branch. `updatedKind: 'file'` means the version changed but no commit names it, so it's the file's last change; only show "Updated n days ago" for `'version'`.
- The first run reads 400 days of history (about 45s and 330MB for core and cask); later runs read the week before the last run and carry everything else over in `state/packages.json`. Anything older than the tracking window is `null`: added or updated "over a year ago".

### Trends
Change of the last 30 days against a baseline, on install-on-request for formulae and installs for casks:
- With a snapshot from exactly 30 days earlier: against those 30 days (`basis: previous-30-days`, label "vs. previous 30 days").
- Until then: against the average 30 days of the previous 60, which the 90-day window gives as `(d90 − d30) / 2` (`basis: previous-60-days-average`, label it that way).
- No trend below 100 installs in 30 days or a baseline under 50, or for packages added inside the baseline period.

### Libraries
A formula is flagged `library` when under 30% of its yearly installs are on request (under 50% for `lib*` names), which hides openssl@3, libpng, pcre2 and sqlite but keeps git, jq, ffmpeg, node, curl (38%) and cmake (48%). Under 100 yearly installs, only the `lib*` name counts. `content/overrides.yaml` corrects individual cases.

### History
Homebrew only publishes rolling windows, so the installs-over-time chart comes from our own daily snapshots of the 30-day counts, stored by month in `state/history/YYYY-MM.json` and keyed by the analytics end date (re-running a day replaces it). There's no public archive to backfill from: history starts on 28 Oct 2026. Until there's history, show only the stat cards. The chart plots the rolling 30-day count; label it that way.

## Output (`data/site/`)

| File | Contents |
|---|---|
| `packages.json` | Every official formula and cask (including disabled ones, flagged), plus community packages from the top taps with an install in the last year or added in the last 30 days. See `Package` in `scripts/data/types.ts`. |
| `taps.json` | The top community taps: GitHub details, 30-day installs, listed packages. |
| `history.json` | Snapshot dates and, per package, the 30-day counts on each date. |
| `meta.json` | Analytics windows, tracking windows, counts, warnings from the run. |
| `icons.json` | The CaskFlow commit and the cask tokens it has an icon for (`scripts/data/icons.ts`). Pages load the images from jsDelivr pinned to that commit; only official casks use them. If CaskFlow can't be reached, its list shrinks by half or the file isn't one we'd write, the run keeps yesterday's file. |
| `caskflow-categories.json` | CaskFlow's release tag, its category names, and each cask token's primary category (`scripts/data/categories.ts`). `content/categories.yaml` maps CaskFlow's categories onto ours. Same keep-yesterday rules as icons, plus: a download over 16 MB, or a release that files casks under an id no category maps, keeps yesterday's file with a warning until the mapping is added (`npm run validate:content` fails on such an id). |

Curation (`content/`: categories, picks, collections, overrides) is joined at build time, so editing it only needs a push.

Snapshots live on the `data` branch for now (about 150KB a day). Moving them to Cloudflare R2 is on the roadmap.

## Enrichment crawler (M5 phase C, in progress)

`scripts/crawl/` reads what Homebrew doesn't have: each package's homepage, its GitHub repository and README. Nothing it gathers reaches the site yet: the weekly `crawl.yml` job and the hand-off to the site are in place, but the AI step (`scripts/crawl/enrich.ts`) waits for the owner's choice of models and keys (docs/plans/M5-enrichment.md).

- **`fetch.ts`, the only way out to the web** for URLs taken from package data: http(s) on ports 80/443, no credentials in URLs; every address the host resolves to must be public (loopback, private, CGNAT and Tailscale, link-local including 169.254.169.254, multicast, reserved, and IPv6 outside global unicast are refused), and the connection is pinned to a checked address: IPv4 first, then the next address when one doesn't connect within 5 s (some hosts answer on only one family; GitHub's runners have no IPv6). At most 3 redirects, each checked again; 15 s for the whole request (DNS, robots.txt and every redirect included, waiting for the host's turn not counted); 2 MB after decompression; HTML for pages, image formats sniffed from the bytes; robots.txt per RFC 9309 (`robots.ts`: a 5xx or no answer means stay out; wildcards matched in linear time, so a hostile rule can't stall the crawl); one request a second per host; user agent `brewhunt-crawler (+https://github.com/Oni-giri/brewhunt)`.
- **`extract.ts`, no AI:** the homepage's title, description, visible text (20 KB at most), icon links and web manifest, and the GitHub repositories it links to. A linked repository is the package's own only when its homepage points back at the package's homepage host (same host, or one inside the other; never a code host). Icon candidates (at most 20 icon links read from a page, 30 fetched per package) in order: the homepage's apple-touch icon, manifest icons, SVG and large page icons (`/apple-touch-icon.png` is tried when none is declared), then devicon, dashboard-icons and the GitHub organisation's avatar (only when the organisation is named after the package), with Simple Icons' glyph last. Code-host homepages (GitHub, GitLab, SourceForge, gnu.org…) give no icons. README images drop badges and badge hosts, SVGs, avatars, images whose alt text says logo or sponsor, and images shown under 400px (the rest, sponsors named only by brand included, is for the screenshot classifier); they may be up to 8 MB (animated demos), since each is re-encoded before it's stored. A homepage that only forwards with `<meta http-equiv="refresh">` is followed one hop.
- **`github.ts`:** repository details and README text through GraphQL, 20 repositories a query.
- **`images.ts`:** sizes and a 64-bit difference hash, decoded by sharp with a 50-megapixel limit. Homepage icons under 128px and any icon under 64px are refused; so is an image that looks like another package's (a host's or vendor's default).
- **`dry-run.ts`:** runs all of the above locally into a folder (`--top N`, or `--answer-key N` for the most installed packages without a CaskFlow icon), recording every candidate and why it was refused. **`contact-sheet.ts`** serves that folder for the owner to pick the right icon per package (a candidate, "none" for the letter tile, another URL, or "findable": the right icon isn't among the candidates but a cheap model with search should find it); `--export` writes the answer key to `tests/fixtures/answer-key/icons.json`. **`icon-check.ts`** has a vision model (GLM 5.3 Flash through Inco, `INCO_AI_API_KEY`; about $0.08 for 300 packages) make a first pick for each package. The sheet shows it as a preset the owner confirms or changes, and only confirmed picks count; the export records the model's pick next to the owner's, to measure it. For the packages the owner marked findable, **`find-logos.ts`** looks further (`logos.ts`): the logo the homepage marks or shows in its header (images and inline SVGs), the logo at the top of the README, then the maker's, which the owner accepts when the tool has none of its own: the GitHub organisation's avatar and the icons of the maker's site (the homepage's parent domain, or the organisation's website). `icon-check.ts --findable` presets a pick on a second sheet. For the packages still without a logo, a search agent can propose image URLs: dsh (DeepSeek's harness) with its model on Inco and TinyFish's search and fetch (`~/brewhunt-crawl/dsh-inco.patch.yml` plus the TinyFish MCP patch, read-only, telemetry disabled; Inco itself runs no web search). `find-logos.ts --suggested <file>` takes its URLs as `web-search` candidates, fetched and checked like the others, and `icon-check.ts --findable --ids …` picks those packages again. `contact-sheet.ts --update` folds the owner's answers back into the answer key, marked `findable: true`. **Scoring the icon pipeline:** `dry-run.ts --ids tests/fixtures/answer-key/icons.json` crawls exactly the key's packages, with the logo and maker sources included (`logos.ts`, `site.ts`). `rank.ts` orders the candidates (source order fitted on the owner's answers, then SVG, then size) and makes the rules' pick, which never takes the maker's logo or an image the page or README doesn't call a logo. `icon-check.ts --judge --out judge-picks.json` has the vision model choose among the ranked candidates. `score.ts --from <dir> --rules` (or `--picks <file>`) sorts each answer into exact file, same file (perceptual hash within 4 bits), other file, icon where the owner wants the tile (wrong), missed, and tile. A hash only proves the same file: one logo drawn again can differ by up to 44 of 64 bits. The key records the hashes of every image the owner was shown (`seen`), so the scorer separates a pick the owner passed over from one the owner never saw; **`review-sheet.ts`** puts both kinds in front of the owner (wrong, also fine, or better), and `--update` records the verdicts in the key as `rejected` and `accepted` hashes. **`jev-judge.ts`** asks TypeSafe's Jev decision model the same question (`JEV_API_KEY`; a Choice, an any-fits Noul and one Noul per candidate in one request, images padded to its 280px minimum) and writes three picks files for `score.ts`; a measurement, not part of the pipeline. **Checks on the AI step's text (`checks.ts`, M5 C7):** the dry run writes each package's `sources.json`, the homepage's visible text and the README as plain text (`readmeText`: no code, images, HTML or link targets; 20KB at most), which is what the summary step reads. Every summary sentence and bullet must quote those sources exactly (whitespace and curly quotes aside; offsets checked when given); every number in digits must appear in its quotes (read in compatibility form, so full-width digits and letters count as plain ones; other scripts' digits drop the sentence); no links, HTML or markdown; every other catalog package named in a sentence must be named in its quotes; length limits; tags short and lowercase; the category one of the catalog's. A failing sentence is dropped, never repaired, and the counts before dropping are kept for the quality gate. **Assets (`assets.ts`, M5 C9):** a chosen icon or screenshot is decoded with a pixel limit and re-encoded to WebP, which drops its metadata (EXIF, location, colour profile: converted to sRGB first) and anything an SVG could run. Icons are 128px squares on transparency; screenshots fit in 1600 × 2400 and are never enlarged. An SVG is checked before it's first decoded (at most 1 MB, nothing outside itself); its render can't be stopped midway, but librsvg's limit of 500,000 referenced elements bounds the worst at a few seconds. Refused: ICO files (none of the owner's 257 icons is one), SVG screenshots, an SVG that refers to anything outside itself (librsvg loads none of it, but a logo has no need), and a result that's one colour. An animated screenshot stays animated within 300 frames, the pixel limit across all frames and 4 MB; otherwise it becomes a still, the busiest of four frames spread through it (real terminal demos are mostly past the limit: mise's has 4,114 frames). Icons that come out poorly are flagged for the review page, not dropped: `faint` (under 8% of the square drawn), `light` (a pale logo on transparency) and `wordmark` (a wide, flat logo). The key is `<kind>s/v1/<sha256 of the source file>.webp`, so a key never changes what it holds; encoding differently bumps `v1`. Each asset has a record: source URL, revision (the README's blob id, else the fetch time), source and output hashes, licence (an icon: "trademark: identification use"; a README screenshot: the repository's SPDX licence, or none), credit ("Screenshot from the project's README") and basis (owner, judge, rules, classifier). **`takedown.ts`** applies `content/takedown.yaml`: a package listed without hashes loses all crawled text and images (and, on the site today, its CaskFlow icon), listed hashes remove those images wherever they appear, and the keys to delete from the store are listed for the next run. **`assets-run.ts`** does all this for a dry-run folder into `<dir>/assets/` (a folder standing in for R2) with `manifest.json` and a page to look at. On the answer key's 235 icons in the pipeline run: no failures, 722 KB in all (about 3 KB each), 9 flagged (node, whose page colours its logo with CSS, is faint). Uploading to R2 and deleting from it wait for the owner's keys. **Cost guard (`cost.ts`, M5 C10):** a request's worst case counts every input token (counted, or at most a token per byte: no token is shorter, whatever the text), every image at 4,784 tokens (the most one can take) and all of its `max_tokens` (which caps thinking and text together), at list prices, halved for Anthropic's Batches API (Haiku 5.5 $0.10/$0.50 per million, $0.50/$2.50 past 100K tokens; Jev $0.042 per million input tokens, no batches). `CostGuard` plans each batch as the longest run of requests that fits what's left of the run's cap (default $10), keeps one batch out at a time, and takes the next only once the last one's real usage is reconciled; when nothing fits, the run stops before submitting. `packageRequests` lists one package's calls: summary, labels, icon judge and screenshot classifier on Haiku, and Jev's check. **`cost-estimate.ts --from <dir>`** gives a dry run's worst case: on the 30-package run, $0.0066 a package, so a $10 cap covers about 1,500 packages at worst. **The second check on summaries (`jev-check.ts`):** after the deterministic checks, each sentence and its quotes go to TypeSafe's Jev (`JEV_API_KEY`) as one yes/no question in a single request per package; a sentence Jev gives less than 0.5 support is dropped. Only a rate limit is tried again: a timeout or server error may have been charged, so it fails the check, and a reply without usage is charged as the request's size in bytes.

### The `enrichment` branch

`crawl.yml` (weekly, and by hand) runs the crawl in jobs that each hold only what they need: `fetch` (the web, no secrets: `dry-run.ts --top 1000` into an artifact of at most 3 GB), `enrich` (the AI step and its checks, with `ANTHROPIC_API_KEY` and `JEV_API_KEY`; it writes `drafts.json` and the drafts' WebP images), `merge` (`publish.ts`, read-only), `publish` (uploads the new images to R2 with the AWS CLI, then commits; write access, runs no npm code), the site build (`ci.yml` with the new commit) and `cleanup` (deletes the images the site stopped showing, once it's deployed). Until `enrich.ts` exists and its keys are set, the weekly run does nothing; a manual run still fetches.

The branch holds `enrichment.json` (`scripts/crawl/enrichment.ts`): the run, the asset base URL (the `ASSET_BASE_URL` repository variable) and per package the `published` item and the `pending` draft waiting for review, each with its sources (URL, revision, text hash), cited summary sentences and bullets, tags, category, icon and screenshot records. A draft waits for review on the whole first run (until anything is published), for every community package, and when the package's sources changed since what's published; otherwise it publishes directly. The owner approves or rejects a draft by its hash in `content/approvals.yaml` on `main`: the site shows an approved draft from the next build (`src/lib/enrichment.ts`, `shownItem`), and the next crawl promotes it (and won't ask again about a rejected one). `content/takedown.yaml` wins over both, on the site and on the branch. The store holds the keys the file refers to: a run uploads the keys it adds and deletes the ones it drops, listed in `removed` so a failed delete is tried again next run.

CI checks the branch out as `enrichment/` next to `data/` (`npm run enrichment:pull` locally); without it the site builds as before. The build stops when `assetBase`'s origin isn't in `public/_headers`' `img-src`, and `publish.ts` checks the same before the branch gets the file. On the site, a crawled icon stands in where CaskFlow has none; the summary, tags and screenshots wait for the app page's redesign (phase D).

## Not available from Homebrew

App icons, screenshots and rich descriptions. Official Mac apps get icons from CaskFlow (above); formulae, community packages and the casks CaskFlow lacks use the generated initial-letter tiles from the design. Later: developer-claimed listings can upload these.
